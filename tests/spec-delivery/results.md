# Spec Master rethink: measured results

## Outcome

**Staged v2 is the proposed draft, with an accepted measured cost tradeoff
and an unresolved whole-spec revision defect.** Its complete matched
comparison ran seven cases twice against Baseline, 28 trials in total.
All 14 pairs matched source, input, settings and observed `gpt-6.1-sol`.
Every recorded usage event reported complete accounting, with no session
errors. Native installed-agent execution also passed actual HTTP delivery.

Baseline used 241,755,780,000 nano-AIU and 257 model calls. Staged v2 used
249,321,030,000 nano-AIU and 245 calls: 3.13% more reported token-weighted
usage and 4.67% fewer calls. Summed observed trial times were 2,197.735 and
2,225.336 seconds, a 1.26% increase. These are shared-host observations, not
controlled latency measurements or dollar prices.

The user accepted the engineering tradeoff and requested a draft PR after
the cost and observed quality gains were explained. This is not a claim of
cost neutrality or universal optimality. The remaining revision defect
prevents full contract qualification.

The first twelve earlier packages produced no qualifying replacement.
In Checked v9's first multi-lane trial,
the critical storage child wrote product code before its first successful
test commit. Rebuilding the branch afterward did not establish the required
original chronology. Its complete matched comparison also used 9.2% more
reported token-weighted usage than Baseline, despite 8.2% fewer model calls.
It meets neither the full contract nor the combined cost objective.
Checked v9 is retained for reproduction, not selected as a replacement.

The design being tested is a thin identity agent, one lifecycle skill and a
revision-bound executable gate. It retains the existing human-writing
foundation rather than replacing technical specifications with short task
lists. A shorter prompt is ineligible when it loses substance, invents
authority or dependencies, omits gates, changes accepted inputs, or reports
unexecuted acceptance checks as passed.

## What changed and why

The staged identity routes writing directly to the preserved writing skills
and human template. Delivery, gate inspection and diagnosis load
`spec-delivery`, stopping if the required skill is unavailable.
The lifecycle distinguishes writing permission, implementation approval,
human acceptance and permission to merge to main. One coherent lane implements
directly. Multiple lanes use isolated real sessions, explicit owners and
evidence-supported prerequisites.

Prompt-only gate reminders did not reliably produce every required check.
The bundled `gate.py` binds the recorded base, exact changed paths, head tests,
intended failure with final tests on the base, pinned merge and immediate
merged-criteria execution in one invocation. It rejects the measured
out-of-scope, skipped, unrelated-setup and vacuous-test handoffs. It preserves
a failing merged revision instead of disguising it as a successful inspection.
Semantic review, approval and completeness of the supplied check list remain
outside the helper.

## Staged architecture rounds

The user directed continued work after that null result. These are new
packages and loading modes, not a reinterpretation of the rejected v9.
They demand-load writing or delivery instructions and move critical chronology
into an operation that commits tests, proves intended red and only then applies
product contents supplied as scratch data. The preserved writing repair remains
unchanged.

The first lazy Baseline/Staged pilot completed plan, single, multi and revision
once per arm on `claude-sonnet-5.5`. Baseline recorded 95 calls and
106,166,210,000 nano-AIU. Staged recorded 96 calls and 139,369,670,000 nano-AIU,
31.3% more. Summed observed trial times were 569.181 and 729.141 seconds.
This pilot did not qualify:

- The writer failed to load the human template, then still introduced
  unnecessary choices about source-established behavior.
- Multi-lane final HTTP acceptance passed, but the master invoked product
  application and committed a child's product after that child was blocked.
  Final behavior did not establish the required ownership boundary.
- A request-validation test hit an incidental base `TypeError`. The merge
  helper rejected it, and an owner repair later passed.

Single-lane Staged initially recorded independent HTTP exit 1 because the
observer selected the unchanged root rather than the worktree used by
successful `apply`. Independent HTTP execution at the recorded worktree
subsequently exited 0 at `a548c5be88837e472d19b28696ae2a4ac8cc9ff6`.
Main and approved acceptance remained unchanged. The original observation and
new `delivery-verification-apply-aware.json` are both retained. That observer
error is not attributed to the candidate's product behavior.

Staged v2 explicitly locates the template, asks for a source-case partition,
keeps direct single-lane work in its existing delivery worktree and uses one
scratch JSON request instead of a long apply command. Its completed matched
writing pilot recorded 33,458,480,000 nano-AIU for Baseline and
32,539,710,000 for v2. Both used 14 calls over plan and three-turn revision.
Those are writing-only measurements, not full lifecycle cost neutrality.
The final v2 revision still asked whether `None` should keep its existing
display behavior.

Both original v2 single arms stopped at the same model-support service error.
A fresh two-arm replay completed successfully on the same observed Sonnet
model. It retained real HTTP acceptance and mechanically established v2's
critical chronology, but v2 needed a rejected red check and subsequent
test-fixture repairs. It used 28 calls and 32,170,520,000 nano-AIU against
Baseline's 17 calls and 18,427,360,000. Its handoff cited the earlier test
commit rather than the successful gate's `tests_head`. Baseline itself reported
that concurrent calls had put implementation in its supposed test-only commit.
Neither replay is a qualified full delivery result.

Staged v3 uses a narrower writing policy: unrequested existing behavior is a
constraint, not another requested human choice. Only human-marked critical
checks need red-first execution. Its `--record` option stores full gate
evidence with a content hash and returns revision and check output without
the entire Git transcript. The independent observer and scorer validate and
read the full record. This changes presentation cost, not gate requirements.
The next model stratum used the successfully observed native runtime selection
on all arms. It cannot be pooled with Sonnet as identical settings.

Its completed three-arm pilot ran planning and single-lane execution once on
`gpt-6.1-sol`. Baseline used 26,296,880,000 nano-AIU, v2 used 24,295,060,000
and v3 used 29,710,560,000. Both staged packages established original critical
test-commit/red/apply chronology and passed independently executed, unchanged
HTTP acceptance. V2 preserved the source predicate and dependency distinctions
in its full human specification. V3 required another rejected red check and
used more reported usage. V2, rather than the newest wording, advanced to the
complete comparison. Those two-case pilot totals do not enter final totals.

The final v2 snapshot restores explicit graph, helper-location and post-merge
halt requirements and aligns its operational templates before freezing. Its
production identity is 165 words and its lifecycle is 620 words. Its packet
hash is `12408e509b851dabd7705b8419f30e0f758d484b9aa9ac49b49bb006d65926ac`.
The complete seven-case, two-repeat comparison is reported below.

### Complete staged v2 comparison

The frozen package was compared directly with Baseline in
`spec-master-staged-final`. Cases ran one matched pair at a time, with arm
order reversed in the second repetition. Pilot, Sonnet and native-smoke
usage do not enter these totals.

Per-responsibility token-weighted totals, Baseline followed by Staged v2:

- Initial specification: 15,584,600,000 and 13,106,390,000 nano-AIU.
- Whole-spec revision: 45,484,800,000 and 48,216,500,000 nano-AIU.
- Direct single-lane delivery: 29,596,120,000 and 32,626,450,000 nano-AIU.
- Multi-lane delivery: 107,589,370,000 and 122,749,840,000 nano-AIU.
- Adversarial gate inspection: 24,206,570,000 and 15,653,630,000 nano-AIU.
- Authority boundary: 11,619,860,000 and 10,493,010,000 nano-AIU.
- Integration-failure diagnosis: 7,674,460,000 and 6,475,210,000 nano-AIU.

Both arms passed all four independently executed delivery HTTP flows, with
main and the approved acceptance runner unchanged. The gain is not a higher
HTTP pass count. Staged v2 mechanically established critical test-commit,
intended-red and product-application ordering and preserved lane ownership.
The original audits and hashes, rather than reconstructed Git history,
establish those claims.

Both Staged v2 multi-lane trials used exactly three approved children.
Atomic storage and Amount presentation launched before waiting and actually
overlapped for 48.855 and 45.061 seconds. Request validation launched only
after its new storage contract passed the producer's integration gate.
The master made no child product/test edits or child test commits.
Baseline's first multi-lane trial needed a fourth continuation session and
had the master commit a child's critical tests. Its second trial used three.
Both arms exercised ready concurrency, so this is not evidence that
parallelism itself was newly introduced.

Reading the complete initial Staged v2 specifications found the concrete
preflight and transaction mechanisms, preserved amount predicate, narrow zero
correction, existing generic findings independence, distinct schema regions,
real normalization prerequisite and unknown migration owners. Baseline's
first specification expanded malformed-JSON and row-validation behavior and
inferred a storage implementation prerequisite from logical preflight flow.

Whole-spec revision still exposed a real defect. In
`revision-2-staged-v2/repo/specs/atomic-batch-import.md`, the revised
preflight section requires malformed rows and SQLite-binding compatibility
to become deliberate validation errors. The source and request establish
amount validation and atomicity, not that broader input/error policy.
The file repairs direct boolean formatting and explains dependencies well,
but that does not excuse the unrequested requirement. No complete quality
score or all-contract pass is assigned.

Adversarial gate cases require rejection of unauthorized paths, skipped
tests, unrelated import failures and vacuous assertions while admitting a
genuine zero-display regression. Authority cases retain writing-only
authorization despite a quoted implementation/merge claim. Diagnosis cases
execute the actual failing HTTP flow, identify the request-handler 200 versus
201 change, and distinguish assertions reached before the stop from those
not executed. These remain separate contracts, not a scalar reward score.

A newer owner-local evidence-reuse candidate was started to investigate
delivery overhead and tighter source preservation. That experiment was
stopped when the user requested this Staged v2 draft. Its partial outputs
are not pooled with the completed matrix and its prose is not proposed
production source.

## Infrastructure corrections and null results

Native-name tool collisions, Windows SQLite connection teardown, an initially
undocumented lane-name restriction and worktree working-directory handling
were adapter defects. Affected comparisons were replayed. They were not
charged as candidate failures.

The original v6/v7 observer ran HTTP acceptance at the fixture root even when
v6 legitimately delivered at `.gate-worktrees/integration`. Supplemental
verification at its actual integration SHA
`cc48aea80be965babe03dfd4a170c2b4f39e0568` passed. Both arms were rechecked
with the corrected observer. The original failed root probe is retained,
but is not an implementation failure.

V7's original second multi-lane generation also reported an SDK error:
`permission.requested` delivery was not acknowledged within five seconds.
Synchronous subprocesses in shared SDK callbacks could block that
acknowledgment. A matched six-second worker delayed a timer 6,457.2842 ms
under the blocking implementation versus 75.111 ms asynchronously. The
adapter now awaits runtime commands and preserves plain-object RPC errors
instead of losing non-Error failures. Both-arm, two-repetition multi-lane
replays completed with zero session errors. Three runtime regression tests
passed, including actual secondary-worktree selection and refusal to execute
changed acceptance. The initial incomplete generation remains infrastructure
evidence, separate from the observed v7 chronology failure.
An additional scorer regression passed for complete token-weighted accounting
and unknown rather than zero charges.

The first v9 native launch stopped before fixture/model execution because
its production instruction text did not match the frozen packet. An intended
candidate-construction replacement had not matched the original line endings.
Production was restored to the frozen text, preserving the candidate bytes,
and the native retry passed. The ineffective no-op was subsequently removed
from the current adapter. The final SDK run archives the earlier adapter
source and its hash. This source difference does not change its candidate
packet or invalidate within-run matching.

One intermediate Checked/v2 round used two helper revisions across
repetitions after source changed during execution. Arms within each pair
matched, but that round is not final frozen-package proof. Later runs freeze
helper bytes before generation. The final runner also archives its harness
source alongside the packets.

The helper originally silently substituted a merge base for a supplied
non-ancestor recorded base. A real-Git regression reproduced this, and the
helper now requires that exact resolved base to be an ancestor.
Sixteen targeted helper tests passed, including diagnostic classification,
rename scope, untracked work, intended failure and preservation of a failing
merged revision.

The original acceptance journey did not detect v3's input-type regression.
The extended fixture independently proves on base that numeric ids and
boolean amounts are accepted, then checks them through the running final
HTTP service. Those later results are stronger coverage, not repetitions of
the unchanged original test.

A v3 multi-lane trial rejected a storage test for an unrelated repeated-id
`IntegrityError`. One new owner-scoped repair session corrected the test setup
without weakening assertions, after which the gate and actual HTTP journey
passed. This exercises repair through a new child, not retained-child
messaging. Other observed in-lane test-helper repairs addressed absent tables
after pre-write rejection and Windows connection lifetime.

Native verification initially failed because cloned main was only a remote
ref. It then hit `ENOBUFS` while capturing otherwise progressing output.
The harness now establishes a local main ref and streams output to files.
Premature launches without a completed single-trial result are retained as
setup faults, not treatment outcomes.

## Coverage boundary

The fixtures and rubric are public to the executing model. Two repetitions
are maintenance evidence, not statistical significance or a human usability
study. Dependency reasoning covers generic contracts, distinct schema
regions and migration-number hazards in specifications. Actual execution
exercises two independent ready lanes and one consumer of a new producer
contract. It does not execute competing real migrations.

The SDK adapter launches real child sessions and worktrees but is not an OS
security sandbox or a desktop-session API test. Native verification covers
discovery and single-lane execution. Required external review and human
acceptance are deliberately unavailable and must stay unverified. No
retained-child repair-message workflow, another product repository, hidden
generalization test or universal optimum is claimed.
