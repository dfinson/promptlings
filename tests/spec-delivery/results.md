# Spec Master rethink: measured results

## Outcome

There is no winner among the twelve tested packages. In Checked v9's first multi-lane trial,
the critical storage child wrote product code before its first successful
test commit. Rebuilding the branch afterward did not establish the required
original chronology. Its complete matched comparison also used 9.2% more
reported token-weighted usage than Baseline, despite 8.2% fewer model calls.
It meets neither the full contract nor the combined cost objective.
The candidate is retained for reproduction, not selected as a replacement.

The design being tested is a thin identity agent, one lifecycle skill and a
revision-bound executable gate. It retains the existing human-writing
foundation rather than replacing technical specifications with short task
lists. A shorter prompt is ineligible when it loses substance, invents
authority or dependencies, omits gates, changes accepted inputs, or reports
unexecuted acceptance checks as passed.

## What changed and why

The identity agent now loads `spec-delivery` and stops if it is unavailable.
The lifecycle distinguishes writing permission, implementation approval,
human acceptance and permission to merge to main. One coherent lane implements
directly. Multiple lanes use isolated real sessions, explicit owners and
evidence-supported prerequisites.

Prompt-only gate reminders did not reliably produce every required check.
The bundled `gate.py` binds the recorded base, exact changed paths, head tests,
intended failure with final tests on the base, pinned merge and immediate
merged-criteria execution in one invocation. It rejects the measured
out-of-scope, skipped, unrelated-setup and vacuous-test handoffs. It preserves
a failing merged revision instead of disguising it as a successful inspection.
Semantic review, approval and completeness of the supplied check list remain
outside the helper.

Readback is an actual operation, not a writing slogan. V6's first planning
audit records a write, saved-file read, correction and another saved-file
read. Its final specification correctly distinguishes existing partial writes
from proposed rollback and leaves migration ownership unknown.

That did not solve reporting fidelity. V6's first regression diagnosis both
marked later assertions unverified and claimed "The 400 paths pass: atomic
rejection and duplicate rollback." The actual HTTP test stopped at the
unexpected 200 response before the duplicate request. V7 adds a whole-handoff
check that reconciles every success claim with executed evidence, not just
the final status list.

## Final matched comparison

The final Baseline/v9 matrix completed all 28 trials: seven cases, two
repetitions and two arms. All 14 groups matched source, input, settings and
one observed model. There were no recorded session errors.
The runner used one independent matched case at a time,
with both arms concurrent within that case and submission order reversed in
repetition two. This setting was chosen after observing host memory pressure.
It is not a user budget limit.

Baseline used 220 model calls and 290,040,870,000 reported nano-AIU.
V9 used 202 calls and 316,746,770,000 nano-AIU. Every recorded usage event
had complete accounting. V9 reduced calls by 8.2% but increased the reported
token-weighted charge by 9.2%. The increase was present in both repetitions:
Baseline used 152,221,810,000 and 137,819,060,000, versus v9's
171,147,830,000 and 145,598,940,000.

Per-case values below are billions of nano-AIU, the reported integer divided
by 1,000,000,000. Each pair is repetition one followed by repetition two.
Call counts follow in parentheses.

- Human specification: Baseline 10.64375 / 10.22410 (4 / 4 calls),
  v9 13.15587 / 11.74347 (6 / 5).
- Handoff gates: Baseline 13.40026 / 13.12125 (8 / 7),
  v9 17.30929 / 14.67700 (9 / 6).
- Single-lane execution: Baseline 16.84515 / 21.67389 (13 / 20),
  v9 21.29260 / 17.80585 (18 / 15).
- Multi-lane execution: Baseline 70.69147 / 51.91478 (80 / 50),
  v9 65.01634 / 55.76012 (54 / 47).
- Authority: Baseline 8.78215 / 8.81090 (5 / 5),
  v9 13.90646 / 8.94990 (8 / 5).
- Regression diagnosis: Baseline 7.48938 / 7.71961 (4 / 4),
  v9 8.01507 / 7.93367 (4 / 4).
- Whole-artifact revision: Baseline 24.36965 / 24.35453 (8 / 8),
  v9 32.45220 / 28.72893 (10 / 11).

Input/output/cache-read tokens were 5,106,837 / 116,093 / 4,594,737 for
Baseline and 4,998,885 / 117,387 / 4,376,412 for v9. Input totals include
cached context, so fewer input tokens do not establish lower charges.
Summed trial wall observations were 1,132.265 and 1,160.847 seconds.
They do not establish controlled latency or a threshold for meaningful
overhead.

Both arms passed all four independent final HTTP journeys. Main and approved
acceptance remained unchanged in all eight execution trials. Both started
the two independently ready lanes before waiting. V9 used three lane
children per multi-lane trial and executed three merge gates per trial.
Baseline used four and three children respectively. None of the multi-lane
masters wrote product code or tests. These results establish execution and
readiness behavior on the supplied width-two graph, not qualification.
Baseline's first single-lane run also combined critical tests and product
implementation in one commit, which its handoff acknowledged.

The method has therefore not selected a smaller successful replacement.
Further prompt accumulation is not supported as a solution by these results.
The mechanical helper reliably checks the supplied revision-bound evidence,
but does not enforce the temporal order of earlier child edits. A future
test of tool-enforced phases would be a different design and experiment,
not a retrospective pass for any of these packages.

The original v6/v7 matrix produced 28 records, with one incomplete SDK
generation. Its unaffected cases remain evidence, including v7's disqualifying
single-lane chronology. Both arms and both multi-lane repetitions were
replayed with asynchronous callbacks: all four delivered the actual HTTP
journey with main and approved acceptance unchanged. V6 used 43/49 calls
and 207.210/191.528 seconds. V7 used 64/44 calls and 329.392/207.659 seconds.
Those are replay observations, not candidate qualification or latency estimates.
The next complete matched comparison, v7 against v8, produced 28 records
in 14 matched two-arm groups. All groups matched source, input, settings and
one observed model. V7 used 204 calls/billing units, v8 used 216.
Their input/output tokens were 5,199,160/134,762 and 5,779,207/135,931.
Both arms passed all four independent final HTTP runs. V8's final writing
failure still prevents selection. These results also do not demonstrate
cost neutrality against the original Baseline.

For comparison, the preceding complete v4/v6 matrix contained 28 results:
14 two-arm groups with matching input, source, settings and a single identical
observed model. V4 used 191 calls/billing units, v6 used 182. Their recorded
input/output tokens were 4,294,943/105,528 and 4,692,347/120,587 respectively.
Each arm passed all four independent final HTTP runs. Neither package
qualified on all contracts.

Legacy billing units are the SDK's `assistant.usage.cost`, not dollars or
token-weighted charges. The scorer now also totals
`copilotUsage.totalNanoAiu`, using a value only when every recorded call has
complete billing telemetry. Missing charges remain unknown, not zero.
This token-weighted field is the primary observed usage-cost comparison.
Calls and usage include actual child sessions. Wall times reflect concurrent service
load and host conditions, not controlled latency estimates. Different
adaptive rounds have different inputs, helper revisions, acceptance coverage
or concurrency settings and are not pooled as identical experiments.

## Installed-agent execution

The v9 native smoke copied the actual source agent and three skills into a
disposable project-local installation and required canonical instruction
parity and exact helper parity with its frozen candidate. It invoked native
`--agent spec-master`, not the SDK's preloaded substitute.

The native process exited 0. Independently executed `python acceptance.py`
exited 0 with two real HTTP/subprocess/SQLite tests. Main and the acceptance
file were unchanged, with zero uncommitted changes. Final fixture revision:
`7e0e6efb701dc3027985fa57282a1a8686da9384`.

Actual telemetry confirms loading `spec-delivery`, `design-writing` and
`reasoning-first-writing`. Test-only commits and intended failing assertions
preceded the product edits: the test commit was `8e2d8bb`, the intended red
run occurred at 19:15:07 UTC, and product edits started at 19:15:53.
The implementation commit was `7e0e6ef`. This successful native trial does
not erase the SDK multi-lane chronology failure.

The earlier native v6, v7 and v8 smokes also passed actual discovery and the stronger
HTTP acceptance. These native single-lane runs do not substitute for assessing
the SDK multi-lane trials or the failed-regression diagnosis.

## Infrastructure corrections and null results

Native-name tool collisions, Windows SQLite connection teardown, an initially
undocumented lane-name restriction and worktree working-directory handling
were adapter defects. Affected comparisons were replayed. They were not
charged as candidate failures.

The original v6/v7 observer ran HTTP acceptance at the fixture root even when
v6 legitimately delivered at `.gate-worktrees/integration`. Supplemental
verification at its actual integration SHA
`cc48aea80be965babe03dfd4a170c2b4f39e0568` passed. Both arms were rechecked
with the corrected observer. The original failed root probe is retained,
but is not an implementation failure.

V7's original second multi-lane generation also reported an SDK error:
`permission.requested` delivery was not acknowledged within five seconds.
Synchronous subprocesses in shared SDK callbacks could block that
acknowledgment. A matched six-second worker delayed a timer 6,457.2842 ms
under the blocking implementation versus 75.111 ms asynchronously. The
adapter now awaits runtime commands and preserves plain-object RPC errors
instead of losing non-Error failures. Both-arm, two-repetition multi-lane
replays completed with zero session errors. Three runtime regression tests
passed, including actual secondary-worktree selection and refusal to execute
changed acceptance. The initial incomplete generation remains infrastructure
evidence, separate from the observed v7 chronology failure.
An additional scorer regression passed for complete token-weighted accounting
and unknown rather than zero charges.

The first v9 native launch stopped before fixture/model execution because
its production instruction text did not match the frozen packet. An intended
candidate-construction replacement had not matched the original line endings.
Production was restored to the frozen text, preserving the candidate bytes,
and the native retry passed. The ineffective no-op was subsequently removed
from the current adapter. The final SDK run archives the earlier adapter
source and its hash. This source difference does not change its candidate
packet or invalidate within-run matching.

One intermediate Checked/v2 round used two helper revisions across
repetitions after source changed during execution. Arms within each pair
matched, but that round is not final frozen-package proof. Later runs freeze
helper bytes before generation. The final runner also archives its harness
source alongside the packets.

The helper originally silently substituted a merge base for a supplied
non-ancestor recorded base. A real-Git regression reproduced this, and the
helper now requires that exact resolved base to be an ancestor.
Sixteen targeted helper tests passed, including diagnostic classification,
rename scope, untracked work, intended failure and preservation of a failing
merged revision.

The original acceptance journey did not detect v3's input-type regression.
The extended fixture independently proves on base that numeric ids and
boolean amounts are accepted, then checks them through the running final
HTTP service. Those later results are stronger coverage, not repetitions of
the unchanged original test.

A v3 multi-lane trial rejected a storage test for an unrelated repeated-id
`IntegrityError`. One new owner-scoped repair session corrected the test setup
without weakening assertions, after which the gate and actual HTTP journey
passed. This exercises repair through a new child, not retained-child
messaging. Other observed in-lane test-helper repairs addressed absent tables
after pre-write rejection and Windows connection lifetime.

Native verification initially failed because cloned main was only a remote
ref. It then hit `ENOBUFS` while capturing otherwise progressing output.
The harness now establishes a local main ref and streams output to files.
Premature launches without a completed single-trial result are retained as
setup faults, not treatment outcomes.

## Coverage boundary

The fixtures and rubric are public to the executing model. Two repetitions
are maintenance evidence, not statistical significance or a human usability
study. Dependency reasoning covers generic contracts, distinct schema
regions and migration-number hazards in specifications. Actual execution
exercises two independent ready lanes and one consumer of a new producer
contract. It does not execute competing real migrations.

The SDK adapter launches real child sessions and worktrees but is not an OS
security sandbox or a desktop-session API test. Native verification covers
discovery and single-lane execution. Required external review and human
acceptance are deliberately unavailable and must stay unverified. No
retained-child repair-message workflow, another product repository, hidden
generalization test or universal optimum is claimed.
